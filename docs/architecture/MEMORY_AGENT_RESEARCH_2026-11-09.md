# 类人记忆与语义请求编排调研

日期：2026-11-09。状态：调研交付；**未实施、未安装新依赖、未更换模型或数据库**。本文中的拟议接口与参数均为设计建议，不能视为现有功能。调研核实范围与推荐见第3、5、8、9节。

## 1. 目标和证据边界

用户期望：跨任意时间的个人记忆、不同措辞下的语义理解、不编造经历、正确选择查询/联网/日程等动作，以及回答「你觉得我近期最有意思的一件事是什么」。随后明确要求先调研成熟产品和开源方案，再动手。

本文区分三类陈述：

- **公开产品事实**：厂商官方帮助或公告明确描述的功能与限制。
- **公开工程方法**：论文、开源项目或工程文档公开的方法；不能因此推断豆包、ChatGPT 内部采用了同样实现。
- **项目建议**：结合现有源码提出的设计，尚未经本项目实施和验收。

没有证据支持任何方案能在任意输入、无限历史下保证逐条永久精确召回或绝对零幻觉。模型不应把每次聊天直接当成新的训练参数；可持久存储、检索并带入本轮上下文，是另一种机制。

外部资料采用官方站点、官方仓库和论文入口；部分网页全文抓取受当前工具网络限制，需区分官方页面的可检索摘要与直接读到的正文。开源自报测评不得当作本项目实测，不把旧论文的模型得分外推为当前商业产品表现。

## 2. 对五项诉求的拆解

| 诉求 | 应落实的能力 | 不能偷换成什么 |
| --- | --- | --- |
| 不论多久仍能反应 | 已授权且成功保存的历史无默认年龄截断；原始用户来源可查、索引可补建 | 只保存少数摘要，却宣称每句话都记住了 |
| 不同词、同种意思 | 模型理解完整语义、上下文和指代；多种查询表述 + 语义向量 + 重排 | 固定同义词表或字面命中率 |
| 不出现幻觉 | 个人事实须有来源；日期、地点、数额、状态可核验；不足时明确说明 | 加一句「不要编造」就视作零幻觉保证 |
| 真正理解需求 | 有类型的工具调用/计划、后端校验、多意图拆分、业务回执 | 将全部非空输入都当成同一种向量查询 |
| 模糊复杂回顾 | 时间范围内事件概览、分组/覆盖统计、可追溯摘要，再作有标识的主观选择 | 只把「有意思」当作检索词，或拿 top-8 当完整历史 |

「用户曾提到」仍受授权、撤回、保存失败等条件约束；撤回后的资料不能为了提高召回而重新出现。

## 3. 成熟产品的公开能力

### 3.1 豆包：从对话总结相关信息，保留量与更新均有限制

已直接读取[豆包《记忆功能FAQ》](https://www.doubao.com/legal/memory_faq)官方正文。页面未标发布时间，查阅日为2026-11-09。

- 自动记忆由模型从历史对话总结，作为未来回答背景；官方原文为「模型可能不会记住对话中的所有细节」。自动记忆按周期刷新，无法实时更新。
- 明确要求「请记住……」可随指令实时变化，用户可在记忆面板逐条查看、删除。
- FAQ说明保存总量有上限，达到上限后，最近保存的记忆会覆盖最早保存的记忆；没有公开具体容量。
- FAQ列举的来源是对话文本及实时通话转写，不包括上传的图片、文件、链接或视频画面。
- 关闭功能和删除聊天均不等于删除记忆，删除记忆后停止引用也可能有延迟。

由此可确认豆包具有跨对话提炼与使用个人信息的功能；不能宣称其无限保存每句话、永久100%召回。FAQ没有公开其具体向量模型、数据库、重排器、任务规划协议，也没有给复杂回顾的完整性保证。

### 3.2 ChatGPT：按需选择相关背景，历史参考不等于全部准确记住

已直接读取OpenAI官方[Memory in ChatGPT](https://help.openai.com/en/articles/8590148-memory-in-chatgpt)。2026-11-09页面显示相对更新时间「8天前」，未据此推定首发日期。

- 官方明确：「Memory does not retain every detail from every conversation.」
- 可使用历史聊天、已保存记忆等相关信息，具体受套餐、地区、功能版本及用户设置影响；已保存记忆与聊天记录分开存储。
- 官方说明不会为每条回复都搜索历史，而是在相关背景可能改善回答时使用。摘要是高层概览，不能视为完整历史明细。
- 某些回答可显示个人背景来源，但来源展示也不保证列出影响回复的所有因素。
- 帮助中的「历史参考没有单独存储限制」只描述该功能的存储限制，不能换成「每句话永久准确记住」「每次都遍历全库」或「检索必定命中」。

官方还确认[按需联网与查询改写](https://help.openai.com/en/articles/9237897-searching-the-web-with-chatgpt)：模型可以将请求改成一个或多个查询，结合相关记忆使搜索更贴合用户，必要时继续搜索。该文也指出搜索结果和引用可能不完整、过时或错误。页面查阅时显示「20天前」更新。

[Scheduled tasks](https://help.openai.com/en/articles/10291617-scheduled-tasks-in-chatgpt)则是可查看、修改、暂停或删除的真实一次性/重复任务，并有独立确认与通知设置；查阅时显示「8天前」更新。记住某个计划和成功创建提醒是两种能力，不能把聊天中的「我记住了」等同任务已执行，更不能直接推为已写入外部日历。豆包App对应的可靠定时任务能力及其内部路由，本次未找到足够一手证据。

OpenAI在2025-09-05的[《语言模型为何会产生幻觉》](https://openai.com/zh-Hans-CN/index/why-language-models-hallucinate/)中明确承认ChatGPT仍有幻觉。它们的成熟体验也不能作为本项目承诺零幻觉的依据。

### 3.3 厂商公开实现示例能证明什么

[火山引擎官方 longterm_memory 示例](https://github.com/volcengine/ai-app-lab/blob/88c983d70a098110fc839f8cd05e29fa7715e6ce/demohouse/longterm_memory/README.md)公开了一条可复用的方法：LLM提取事实 → embedding编码 → 向量存储/相似度检索 → 将相关事实交给对话模型。示例使用旧版Mem0、DeepSeek-R1、Doubao-embedding、VikingDB；README还单独介绍了火山记忆库云服务的画像、意图识别、问题改写、冲突处理和清理能力。

这是公开技术示例与另一项云服务的说明，**不能据此断言豆包App内部使用Mem0、DeepSeek-R1或VikingDB**。示例的聊天内主动提醒也不构成脱离聊天的可靠定时推送证明。示例依赖的旧版Mem0与第5节本次核实的新算法不同，不能混用配置或能力结论。

长上下文描述一次模型调用可处理的材料规模；产品记忆描述哪些信息可持久保存、更新，并在未来重新选入上下文。记录仍存在、材料被选入、最终回答正确，是三个需要分别验证的条件。两家消费产品的完整内部检索与调度算法仍属未知。

## 4. 可公开解释的工程方法

### 4.1 两种存储目的，加上来源链

建议同时维护：

1. **原始用户来源**：保存已授权原话、用户/会话/消息身份、记录时间和来源，作为证据与重建入口。不把助手生成的个人经历混进去。
2. **语义记忆**：提炼稳定偏好、人物关系、具体经历、计划和变化，便于搜索和个性化。
3. **可回溯摘要与索引**：日/周摘要、事件分组、语义向量及来源关联，可重建，不能代替唯一原始证据。

个人事实的记录时间和实际发生时间应分开；未知发生时间不擅自补全。状态变化保留版本与有效区间，不能简单将最近一次写入当成所有历史的答案。

### 4.2 LLM 先理解，再通过受约束工具获取证据

建议优先复用 LibreChat 已有的模型工具调用机制。用户说的「拆解」可以直接表现为结构化工具参数，不必机械地每轮固定串行增加一遍独立 planner 和一遍 query rewrite。

示例工具职责（拟议）：

- `search_personal_memory`：含义明确的长期主题/事件检索。
- `list_personal_events`：时间概览、数量和有代表性的近期经历。
- `query_reminders`：真实任务状态查询。
- `prepare_reminder`：创建/修改草稿；最终成功由既有业务服务确认。
- `search_web`：确有需要并有已启用的搜索能力时联网。

也可采用独立结构化 planner，但必须计入延迟和成本、避免重复模型调用。两者需在小规模对照实验后选择，不能只因架构看起来完整就引入多个框架。

计划可以包含任务列表、语义主题、至多少量不同表述、时间约束、需要澄清的字段。不可由模型指定权威用户身份、权限、任意 SQL、外部服务 URL 或「已创建成功」状态。

### 4.3 泛化查询是找证据的假设，不是事实

假设原记录为「带家里的猫去打疫苗」，新输入为「毛孩子那次预防针还记得吗」。模型可将后者解释为宠物接种相关语义查询，再由后端寻找已存记录。

生成的不同查询表述只用于查找；在命中之前，不可把假设当作「你确实养猫、去过宠物医院」的证据。不引入静态同义词表、内容关键词匹配或词法兜底，维持本项目的纯语义约束。

### 4.4 概览与主题搜索采用不同查询方式

「近15天我做了什么」用授权用户 + 实际事件时间范围查询，不要求每件事情与「做了什么」达到统一相似度阈值。

「近期最有意思的一件事」则先取得近期事件中有覆盖和多样性的候选，再依据记录内容做主观推荐。资料不足时不能臆造，资料不全时说明范围。回答措辞应为「在目前查到的经历里，我会选……」，不能擅自声称「这是你最开心的一天」。

模糊「近期」应采用产品可配置默认窗口并明确告知。用户没有时间限制时，长期主题检索不自动套近期窗口。相同内容发生在不同日期时，可合并展示次数和日期，但不可丢掉独立经历。

### 4.5 控制时间和 token

- 入库后台完成编码与索引，不把全库重新编码放到每轮请求。
- 先按用户/权限/时间等结构化条件查询；大规模语义搜索再评估近似向量索引，实际延迟需实测。
- 先查摘要或候选，按需要展开原文；有界检索回合和整体 deadline，避免无限工具循环。
- 具体问答传少量高相关证据；概览传有来源的分组摘要及必要明细，不能靠固定 top-k 声称完整。
- 证据包返回查询范围、合格记录数量、本次覆盖数量、是否截断、是否有更多，不把「查到一部分」说成「只有这些」。
- 使用实际 tokenizer 计量上下文预算，不能把6000字符等同6000 token。预计算摘要亦有更新、撤回和一致性成本。

### 4.6 防幻觉与业务事实边界

- 个人事实来自当前用户原话或授权证据；联网资料和模型知识用于解释与建议，分清来源。
- 引用 ID 必须属于本轮授权证据集合，引用内容还须支持具体断言；存在一个真链接不代表整句话都正确。
- 日期、数量、任务状态优先由后端确定；计划不等于已发生事件，草稿不等于已设置提醒。
- 无命中、无权限、服务不可用、结果不完整分开返回；不能把本次未找到表述为从未发生。
- 对高度结构化的事实采用后端校验或模板输出；对自由文本可以复核来源支持性，但额外 LLM 检查也不是数学保证。
- 写入需保存用户原话、维持幂等和未知结果核对；模型提出动作不授予越权执行能力。

## 5. 开源方案比较

本节基于官方仓库、许可证和文档。没有安装任何候选，也没有运行其中文质量、性能或本项目适配测试。许可证只涵盖核实的开源代码；模型权重、云服务、品牌素材和依赖仍需分别确认。

| 方案 | 许可证与能力 | 纯语义约束及实际限制 | 项目取舍 |
| --- | --- | --- | --- |
| **Mem0 OSS** | Apache-2.0；从消息提炼事实，提供用户域记忆、显式更新/删除/历史等接口，可自托管，支持配置embedding与reranker | 本次核实的新算法是ADD-only自动摄取，新事实与旧事实并存；显式CRUD不等于自动解决冲突。新检索组合semantic + BM25 + entity matching，不能原样采用 | 作为记忆管理设计参考；若做隔离试验，先锁版本并验证不使用任何词面信号。现阶段不建议全量替换 |
| **Letta / letta-code** | Apache-2.0，LICENSE末尾另排除品牌资产；有状态agent，当前MemFS使用文件和Git追踪记忆，部分内容常驻上下文 | 当前MemFS默认没有向量索引；搜索mod有关键词/语义/混合模式。默认文件搜索流程不符合本项目约束，全链路纯语义配置未实测；完整runtime与现有聊天/业务服务重叠 | 借鉴分层记忆与版本管理；现阶段迁移整个agent runtime成本偏高 |

### 5.1 不能沿用旧文章的两项版本事实

**Mem0**：本次直接读取的[固定迁移文档](https://github.com/mem0ai/mem0/blob/f1791daa86d469249c9b002f62644d58a1eb96a0/docs/migration/oss-v2-to-v3.mdx)写明：自动抽取只新增；外部图存储驱动从OSS移除，图记忆转为Platform；BM25与实体评分提升语义候选排名，不扩展候选集合。即使不扩展候选，也仍使用词面信号，不符合本项目严格约束。文档描述缺依赖时降级，并给出底层未加权向量查询入口，但没有在本轮证明一个稳定的全局开关可禁止所有词面处理。不能把卸载依赖、某个分支降级或云版功能当作已验证的纯语义OSS方案。

**Letta**：本次直接读取的[固定主仓README](https://github.com/letta-ai/letta/blob/8816d3a8516893bfdc0fa14bfb1235226012e295/README.md)明确活跃代码迁至`letta-code`，旧V1 API server保存在archive分支。当前路线应核对MemFS与新SDK，不能把旧版core/archival API、旧Docker教程和新文件系统功能混写为同一个现行实现。

### 5.2 撤回与评测的共同边界

删除当前记忆条目，不代表原话、派生事实、向量、摘要、checkpoint、缓存、版本历史和备份都已同步失效。依赖链由本项目负责；保留历史审计也不能使已撤回资料重新参与回答。LlamaIndex索引删除与docstore删除、Letta当前文件与Git历史均需区分。

Mem0官方评测有托管Platform与OSS、不同算法/参数和文档版本的差别；Letta官方实验使用过文件关键词搜索，不能给本项目纯语义路线背书。**不将厂商自报分数排列成可直接比较的榜单**，不把LoCoMo或LongMemEval的公开得分迁移成中文私人经历的承诺。本次没有核实到LangGraph或LlamaIndex针对本项目整条链路的独立准确率结果。

适合采用的思路是：受约束工具与显式流程管理复杂动作；语义检索/改写/重排用于主题查找；时间与覆盖聚合用于回顾；来源校验用于回答。安装一个记忆库不能自行补齐所有层次。

## 6. 当前项目差距（已核对源码）

1. 自动记忆为「原话保存 → 入队 → 抽取 → 校验 → memory_items」，不是全部聊天原话都能从记忆接口检索。
2. 入队需授权；`memory.py` 对超过24小时的任务 payload 会清理，抽取存在重试与失败。长期保留的聊天原话与队列临时 payload 不能混为一谈。
3. `extraction_candidates.py` 每次最多提取8个候选，要求原文证据；无可用抽取模型凭据时回规则。规则能识别的内容不等于自然语言全部含义。
4. 已有持久向量索引会覆盖全部合格记忆，没有按年龄截断；但末端仍经过时间、阈值、top-k和预算，不能保证每种表达都命中。默认 Settings 语义阈值为0.48；测试 fixture/构造器默认值可能不同。
5. 当前没有语义意图计划协议、独立 overview 查询或完整性元数据；`UserRecallRequest` 不接收 plan，不能单端偷偷加字段。
6. 近期范围约束已存在，但概览问题仍走语义阈值，解释了数据库有事件而「近15天做了什么」仍可能 no_match。
7. 聊天侧所有非空文本都尝试召回；query rewrite 的阶段超时4秒，与外层普通请求3.5秒不一致。新增 planner 前应先明确端到端预算。
8. 提醒已具备真实业务链、草稿校验、权限、幂等与 unknown/reconcile；但仍有规则门控，不能只让 LLM 判对而不迁移后端协议。
9. LibreChat 源码已有 web_search 工具与配置/鉴权路径，不能据此断言当前部署已启用或可联网。life-core 没有通用联网适配器。
10. life-core 有模型抽取配置但无独立 planner 配置；运行实例实际凭据可用性本轮未验证。LibreChat 已配置的辅助模型调用路径可以复用，建议密钥留在既有服务端，不导出到 Python 或客户端。

- `services/life-core/app/memory.py:311`、`:327`：入队与抽取生命周期。
- `services/life-core/app/extraction_candidates.py:325`、`:423`：有依据的候选与模型/规则选择。

## 7. 拟议验收方法

建立与调参样本分离的中文测试集，不再只测指定日期和近似原话：

- 跨年旧经历，使用不同措辞查询；评估检索到来源以及回答是否正确。
- 同义表达、指代、多事实合问、否定、纠正后的最新状态。
- 时间概览、按周统计、没有具体主题的主观回顾。
- 一句话内「查记忆 + 创建提醒 + 查外部信息」的混合意图。
- 无记录、无授权、已撤回、抽取失败、索引冷启动、工具超时。
- 恶意或无关内容作为用户数据，不成为后端命令或权威事实。

分别记录：入库覆盖率、检索 recall@k、个人事实来源支持率、错误拒答/无依据作答、路由/时间正确率、业务动作准确性、p50/p95延迟、每轮token/调用数。没有实测数据前不预填目标完成率或宣称接近某商业产品。

## 8. 推荐和待决策项

### 8.1 推荐路线

**推荐保留LibreChat + life-core + Memos官方API + 现有BGE语义模型，以受约束工具调用连接理解、查询和执行；第一版不引入完整的新记忆平台。** LangGraph用于后续确有复杂暂停/恢复需求时的流程层，LlamaIndex用于检索/引用组件的按需复用。Mem0和Letta可借鉴，不建议现在整套切换。后续新增模型仍只允许存放H盘仓库内。

用户原先的「LLM理解 → 后端查找 → 带来源返回 → LLM回答」方向成立，关键要补齐以下合同：

- **存什么**：原始用户来源、提炼记忆与可重建摘要分开，保存失败/抽取遗漏可观察，可从授权原话补建。聊天内容通过现有受控服务读取，不直接跨库拿账号数据。
- **查什么**：模型输出语义意图与工具参数，后端控制身份、权限、时间解析与查询边界。遇到歧义或必要字段缺失再澄清；不靠堆同义词或静态触发词模拟理解。
- **如何查**：长期主题走语义检索；「最近做了什么」走结构化时间概览；真实提醒状态走业务接口；实时外部知识走已启用搜索工具。多意图可有多个受限动作，读取可并行，有依赖的动作按序执行。
- **返回什么**：来源原话/必要片段、实际事件时间和记录时间、证据ID、真实业务结果，以及范围、数量、覆盖与截断状态。查询改写只作为查询，不混入事实包。
- **如何回答**：个人事实有来源，通用知识与主观判断明确区分；无命中/不可用/不完整分别表达。对日期、数量和业务成功状态实行后端校验；自由文本事实支持性仍需端到端评测。

### 8.2 模糊请求的具体处理示例

以下只是拟议执行过程，未实际实现，也没有虚构用户经历：

| 阶段 | 「你觉得我近期最有意思的一件事是什么」 |
| --- | --- |
| 理解 | 个人经历的时间概览 + 主观推荐；若「近期」未限定，采用明确告知的产品默认窗口；不自动联网 |
| 获取 | 按授权和事件时间取得范围内事件；分页/分组控制规模，必要时从摘要展开原文 |
| 整理 | 保留不同事件的代表性，优先参考用户明确表达的新奇、兴趣或感受；未知感受不补造 |
| 判断 | 在已获得证据中选择并说明选择理由；若摘要遗漏可能影响排序，应继续查找或限定结论 |
| 回答 | 「在目前查到的这些经历里，我会选……」并提供来源；证据不足则说明本次无法据此选择 |

回答主观选择不等于证明「客观最有意思」，更不能把查到的部分说成全部经历。一般联网知识无法补齐缺失的个人史。

### 8.3 拟议实施顺序与验收边界

此处为可审阅建议，**本轮没有开始任一实施阶段**：

1. **来源与覆盖**：梳理现有原话到记忆链路，建立可补建、更新/撤回和完整性状态；先让保存成功、抽取成功和可检索分别可见。
2. **语义路由与读取工具**：复用LibreChat现有provider和受约束工具调用，新增主题搜索、事件概览、提醒查询；通用问题按需使用背景。独立planner只在原生工具调用不适配时做对照，不默认每轮重复规划与改写。
3. **证据回答与模糊回顾**：覆盖统计、分层摘要、受限扩展查询、事实来源校验；修复概览仍过统一相似度阈值的问题。
4. **写入与联网编排**：保留既有提醒草稿、权限、幂等和unknown/reconcile；联网先核实实际配置与可用性，依据工具真实结果回答。
5. **统一中文验收**：按第7节运行隔离测试集与真实聊天链路，分别报告检索命中、最终回答、业务执行、延迟和成本；失败项不以框架benchmark覆盖。

各阶段独立验证、归档上游改动和本地提交。需要跨仓库修改时同时审查LibreChat独立仓库说明；不改其他工作树或用户既有Auth改动。本轮不预估未经实测的提速比例、准确率或与豆包/ChatGPT的等价程度。

下一次续接点：以本报告确定实施范围和工具/证据协议，再进入代码改造。当前时间概览漏查、抽取覆盖和部署联网可用性仍未修复或验证。
