## 3. 架构实现（含记忆管线梳理）

### 3.1 概念与关系

| 概念 | 载体/存储 | 说明 |
| --- | --- | --- |
| 聊天记录 | LibreChat MongoDB | 用户原始消息由 LibreChat 持久化，`savedMessage` |
| 意图（识别） | life-core 内存/LLM | `memory.classify()` + `extraction.extract_event()` 判定消息是否含记忆信号：`life_event` / `stable_fact` / `future_plan` / `no_memory` |
| 记忆（结构化） | life-core SQLite `memory_items` | 由意图识别产出的结构化条目：事实（饮品偏好/居住）、计划、生活事件，含 `semantic_key`、`importance`、`confidence`、版本与证据 |
| 回忆（生活事件） | life-core SQLite `events` + Memos | `life_event` 经授权后写入 `events`，发布为 Memos 的 PRIVATE memo，`status=published` + `memo_ref`；「我的回忆」影集即读取这些已发布事件 |
| 长期记忆 | life-core SQLite `memory_items`（长期持久） | 跨会话/跨天保留的语义记忆，通过召回注入后续对话；「长期记忆跨天召回」尚未完成 |

### 3.2 数据流

```text
用户在 LibreChat 发消息
  -> LibreChat 持久化消息（MongoDB）
  -> BaseClient.js queueLifeMemory -> life-core /internal/v1/events/enqueue
  -> memory_jobs 队列 -> 后台线程 process_event
       -> classify/extract_event（意图识别）
       -> memory.save -> memory_items（记忆/长期记忆）
       -> life_event 且已授权 -> create_event -> events（回忆）
            -> publish_event -> Memos PRIVATE memo（回忆正文）
  （后续提问）withLifeMemory -> /internal/v1/knowledge/recall
       -> memory.recall（bigram 匹配 memory_items + 提醒）
       -> 作为「不可信证据」注入模型上下文
```

存储边界：LibreChat MongoDB（聊天/账号）、life-core SQLite（业务索引/记忆/事件/任务/协作）、Memos（回忆正文）。

### 3.3 本次修复的根因与决策

- 根因：`current_identity()`（`/memories`、`/knowledge`、`/moments` 等记忆端点的身份依赖）要求 `users` 表已存在映射；未映射账户直接 `403 USER_NOT_MAPPED`。而前端启动只调用协作端点（`shared-memories`/`notifications`，其 `ensure_profile` 只建 `collab_profiles`，不建 `users`），不会调用 `/api/v1/me`。因此新注册/未 bootstrap 的账户一打开「我的回忆」即 403，页面进入错误态。
- 决策：任何通过 LibreChat JWT 校验的账户，`current_identity` 一律用 `ensure_reminder_user` 建立最小 `users` 行（`memos_user_id=''`、`memory_consent=0`），使只读回忆页降级为空列表而非 403。发布仍由下游 `memory_consent` 与 Memos 映射把关，不扩大权限。
- 附带修复：后台 `work()` 线程中提醒对账（`reconcile_notifications`）因缺 `LIFE_CREDENTIAL_MASTER_KEY` 抛 `CREDENTIAL_MASTER_KEY_REQUIRED`，此前会连带杀死 `memory-extraction` 线程（使记忆抽取停摆）。改为逐任务 try/except，单点失败不再拖垮记忆抽取。
