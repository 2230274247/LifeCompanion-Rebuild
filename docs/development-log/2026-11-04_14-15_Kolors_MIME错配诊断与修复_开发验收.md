## 3. 根因

### 3.1 为什么生图数显示 0

一次性账本在同一运行中已明确写入：

```json
{"status":"IMAGE_REQUEST_REJECTED_OR_FAILED","image_generation_requests":1}
```

旧 `verify_kolors.py` 却要等 `provider.generate()` 完整成功返回后才执行
`record["image_generation_requests"] = 1`。当请求已发出、图片已下载，但后续
MIME 校验抛错时，Verification 仍保留初始值 0。`request_sent` 也因为只从
`ProviderError.status_code/trace_id` 推断而误写为 false。

这是**计数写入顺序和失败诊断传播 bug**，不是“请求未发出”。

### 3.2 MIME 错误发生在什么阶段

旧 Provider 顺序为：

1. `POST /v1/images/generations`
2. 要求响应恰好一张图片并取得临时 URL
3. HTTPS 公网目标检查
4. 下载图片
5. Pillow `verify()` 与重新 `load()` 完整解码
6. 识别 PNG/JPEG/WebP
7. 比较下载响应 `Content-Type` 与 Pillow 实际格式

能够返回 `IMAGE_MIME_FORMAT_MISMATCH`，说明已经通过第 1～6 步；
因此：

- 不是本地 Mock/自检样本；
- 不是账户权限或价格预检失败；
- 不是未下载图片；
- 不是损坏或无法解码的图片；
- 是真实下载结果的 HTTP 声明类型与 Pillow 实际格式不一致。

旧版本没有把下载 `Content-Type`、Pillow 格式、供应商 trace ID 保存到异常，
所以**无法从旧证据精确恢复当时的具体 MIME 值**。必须保留这一事实，不能猜测。
