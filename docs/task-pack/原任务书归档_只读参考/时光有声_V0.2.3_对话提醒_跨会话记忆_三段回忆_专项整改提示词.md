# 时光有声 V0.2.3：对话式提醒、跨会话长期记忆与早中晚回忆闭环专项整改任务书

> 交付对象：Codex（在现有项目代码仓库内执行）  
> 任务来源：用户提供的五张现状截图与 V0.2.2 最终验收汇总  
> 当前基线：V0.2.2 总体 **PARTIAL**。请先核查源码及真实数据库，不得将本任务书的推断当作已确诊根因。  
> 核心产品定位：**自然聊天优先、快捷选择补充歧义、服务端真实持久化、跨对话有效检索、可从聊天进入提醒/记忆/回忆详情**。

## 0. 本轮要解决的问题（必须正面回应）

当前可观察现象：

1. 用户说过事件与时间，系统仍要求重复填“提醒内容、日期、时刻、时区”等大量表单字段。
2. 用户明确表述“明天早上”，体验应类似 Muse：先理解相对日期，针对缺失的**具体几点**弹出数个快捷时间选择，不需要输入一整张表。
3. 对话产生的提醒、记忆、回忆不能从聊天自然跳转至其对应的管理页/详情页，或点击后没有可信的业务结果。
4. 在其他聊天窗口问“之前我让你提醒带什么”，系统似乎仅知道部分内容，无法稳定跨会话找回“绿色 U 盘，不是银色的”“雨伞”等不同事件。
5. 用户取消提醒后，AI 可能还认为它正等待补全信息，出现展示状态与真实业务状态不一致。
6. 用户提出早、中、晚固定三个时间窗，**仅从该时间窗实际聊天中已经持久化的事件记忆**选取最值得回忆的内容；有合适事件时按计划自动生图、静默进入“我的回忆”，而不是要求用户每天确认生图。

**本轮首先确保核心链路闭环，不接受只换提示词、只修改文案、只增加一张卡片、只让模型声称“已经记住”。**

## 1. 硬约束

- 现有产品/代码为基线：先查仓库，再决定具体实现；不要假定前端使用 React Router、Vue Router、Memos、Vikunja 的某个表结构，实际以代码为准。
- 不改变已有冻结的 UI 规范、设计 Token、主导航、已稳定的聊天和推送能力；尽量复用现有组件、设计系统、类型定义、任务服务及数据库迁移体系。
- 保留 V0.2.2 已通过的提醒草稿、确认、撤销、跨账号隔离、真实 Vikunja webhook、ntfy 站内推送、GLM 接入等能力。
- 用户真实历史数据绝对不覆盖、不批量删除、不擅自补写伪造记录；数据库迁移先备份、只作增量、可回滚，生成数据必须使用隔离测试账号和明确标签。
- 不修改上游 Vikunja/ntfy/Memos 镜像源码；通过本项目适配器、服务层和前端工作。
- 未经明确授权，不执行 git commit / push、不部署公网、不擅自改动生产环境配置和管理密钥。
- 不泄露 API Key / JWT / 个人聊天内容；证据截图与日志必须脱敏。
- 不牺牲授权与隐私：长期记忆写入、生成图片、通知推送必须受现有授权状态和用户设置约束。拒绝或关闭授权时，不要绕过用户选择。
- 所有“成功”文案以服务端真实回执为依据；“已提交”不等于“已完成”，“ntfy 已接受”不等于“手机已送达”。
- 任务分阶段开展，每阶段运行测试并生成证据，禁止以删除测试、修改断言或降低验收口径制造 PASS。

## 2. P0：先核查“无法进入页面”的实际根因

请检查所有实际入口，而不只是单个提醒候选卡：

- 聊天中的提醒候选、已创建提醒、已取消提醒卡片。
- 聊天中引用的个人记忆/事件卡片、回忆图片卡片。
- 侧边栏及底部导航中的“提醒”“我的记忆”“我的回忆”入口。
- 相关业务列表页的详情打开与返回。
- 直接刷新详情 URL、浏览器返回、移动端路由与身份校验。

必须沿着 **用户点击 → 组件事件 → 前端路由 → 对应 ID → 后端查询 → 权限鉴权 → 真实页面渲染** 一路追踪。记录真实故障属于哪一层：无点击事件、`preventDefault` 阻断、路由表缺项、错误 query/params、缺失 `reminder_id/memory_id/moment_id`、前后端 ID 不一致、鉴权 401/403、数据 404、组件加载失败、状态缓存过期或其他。

特别注意：V0.2.2 的 `ReminderCards.tsx` 修复了“候选链接滚动到来源消息”，**滚动至来源消息 ≠ 打开任务详情**。应保留“查看原对话”的独立操作，同时增加“查看提醒 / 查看记忆 / 查看回忆”的业务入口，不能两者混用。

### P0 验收

- 从聊天中点击**已创建提醒**，能直接打开**当前账号**的提醒详情；从详情返回原聊天上下文，刷新仍可访问。
- 从聊天中点击**已持久化事件记忆**，进入记忆详情，展示来源、时间与内容（可按隐私设置隐藏）。
- 从聊天中点击**已生成的回忆**，进入“我的回忆”对应图片与事件详情；图片未生成时显示真实任务状态而非空白。
- 侧栏和底栏导航可用，移动端返回行为正确；不存在循环跳转或按钮无反馈。
- 另一账号无法通过替换 URL 中 ID 越权读取别人的提醒、记忆或回忆。
- 不存在对应实体时，不能伪造跳转成功；给出可理解的空状态或未创建提示。

## 3. P0：对话式提醒重做——从填写表单转为“仅补缺失项”

### 3.1 解析与状态模型

实现或修复清晰的服务端状态机，例如：`detected → collecting_missing_info → ready → creating → active → cancelled / failed / completed`。状态名称可与现有系统适配，但含义必须明确。

解析字段至少包括：

- `intent`：用户是否**明确要求**创建提醒；仅闲聊“明天有会”不应无授权直接调度通知。
- `title`：核心提醒内容，精确保留限定条件，例如“绿色 U 盘（不是银色）”。
- `event_date` / `event_time`：事件发生日期和时间，记录解析来源及置信度。
- `remind_at` 或 `lead_minutes`：通知时间；与事件时间严格区分。
- `timezone`：从用户设定或事件地点获得 **IANA 时区**，如 `Asia/Shanghai`，不能将 `1` 当成时区。
- `location`、`source_conversation_id`、`source_message_ids`、`owner_user_id`。
- `status`、`provider_task_id`、`idempotency_key`、`last_verified_at`。

解析相对时间要使用**服务端可验证当前时间 + 用户/事件时区**，不能让 LLM 凭空判断今天是哪天。跨午夜、时区变更、夏令时地区必须有测试。已经可知的信息必须进入结构化草稿；缺什么只追问什么。

### 3.2 交互规则（严格按示例验收）

**案例 A：**“明天早上提醒我带绿色 U 盘，不是银色的。”

- 已有：明天（可解析日期）、提醒主题、颜色与否定约束。
- 缺少：早上具体时间。
- 只问一次：“明天几点提醒你？”提供如 `8:00`、`9:00`、`10:00`、`其他时间` 的快捷按钮；按钮内容根据用户设置和自然语义生成，而非所有场景死板固定。
- 用户点击 `9:00` 后，在已有授权允许的流程下直接调用服务端创建。**不得再次让其填写相同字段或重复确认**。
- 服务端成功后在聊天中显示简洁提醒卡：主题、提醒时刻、状态、“查看提醒”“撤销”。失败则保留草稿，可重试且不能重复创建。

**案例 B：**“明天下午 3 点在 1101 开会，明天早上 9 点提醒我。”

- 所需字段完整，直接创建，不展示日期输入框与时区输入框。
- 明确区分会议时间 15:00 与提醒时间 09:00，卡片显示两者。

**案例 C：**“到杭州后晚上 5 点在中国计量大学开会，提前 2 小时提醒我。”

- 已知：事件 17:00、地点、提前 120 分钟；通知应为**事件当天 15:00**。
- 未知：到底是今天、明天还是其他日期；“到杭州后”不意味着必然是明天。
- 只提供 `今天`、`明天`、`选择日期` 等快捷选项；选择后立即完成，不要求重新填写内容/时间/时区。

**案例 D：**“明天出门记得带雨伞。”

- 没有明确出门时间时，不能伪造 `09:00` 已确定；可以给出时间快捷选项。
- 如果此前已经有**有效且经确认的**出门时间，可使用并明确呈现，避免多问。

**案例 E：**“取消刚才的提醒。”

- 更新真正的服务端状态并同步取消后续调度；再询问时应查询状态并回答“已取消”，不能再说“等待补全”。
- 重试、重复点击、断网恢复不产生重复任务。

### 3.3 UI 体验

- 默认使用对话中内嵌的 2～4 个选项 Chip/轻卡片，点击优先于输入；始终保留“其他时间”入口。
- 时间、日期、时区都明确时应零表单；只有必要且无法给出快捷项时，才提供精简输入控件。
- 提醒卡主要突出“做什么”“什么时候提醒”“是否真正创建”；避免原版大面积多字段表单占据聊天屏幕。
- 用户选完就收起候选项，成功后替换为已创建状态；失败保留输入与选择，并显示可操作的修复方法。
- 卡片必须支持键盘、屏幕阅读器、合理触控尺寸；遵循原设计 Token 与动效规范。
- 过期提醒、时区错误、无权限、推送端不可用等边界必须有明确文案。

## 4. P0：跨聊天窗口的长期记忆——明确“记得”意味着什么

### 4.1 先审计现有实现

绘制真实数据流：

`原始聊天消息 → 记忆候选提取 → 重要性/授权筛选 → 持久化 → 索引 → 跨会话检索 → 证据拼接 → LLM 回答 → 来源详情`

依次核查：

1. 消息是否保存到持久数据库；是否能通过 user_id 关联而不是只靠 conversation_id。
2. 当前是否仅把最近 N 条对话传给模型；当前对话与新的聊天窗口是否拥有不同历史上下文。
3. 是否存在独立的事实记忆/事件记忆表；写入失败时是否误报成功。
4. 记忆检索是否跨会话、有无用户隔离、有无时间/语义/关键词混合召回。
5. 记忆是否覆盖、合并错误或检索 Top-K 太小，导致只召回雨伞而漏掉 U 盘。
6. 记忆删除、撤销、权限开关、来源追溯是否和缓存/向量索引同步。
7. `memory_permissions` 的两行变化（其中一行未归因）为何产生：**先审计证据，禁止直接回滚或偷偷更改授权值**。

### 4.2 产品级记忆模型

至少区分四种信息，不允许混淆：

- **聊天历史**：原始文字与消息列表，按会话保存。
- **长期事实记忆**：偏好、长期有效的个人资料、用户纠正；支持更新、合并、撤回。
- **事件/情景记忆**：有时间/地点/行为/感受/人物的具体经历，关联原始消息，可跨会话检索。
- **任务/提醒**：可执行、有明确状态的提醒实体；不是仅存一条文字记忆。

回忆（文字/图片）属于事件记忆的衍生作品，应保留 `source_memory_ids`、来源日期和生成状态，不应替代真实记忆记录。

### 4.3 检索与一致性要求

- 以用户身份作为最重要的权限边界，在当前聊天无历史上下文时仍可从服务端检索。
- 对“之前提醒我带什么”“除了雨伞还有什么”“我说的 U 盘什么颜色”之类问句，允许检索**多条相关事件**，不能检索到一条后就停止。
- 建议混合召回：结构化数据库过滤 + 关键词匹配 + 语义向量/全文索引；如果已有 Qdrant/其他检索服务，优先复用，不凭空引入更重的依赖。
- 回答附可点击的业务来源入口；若证据不存在，坦诚说“当前记录中未查到”，绝不根据上一轮语言模型生成文本臆测。
- 保存“绿色、不是银色”这类**否定条件和限定词**，不能被摘要压缩丢失。
- 记忆写入与索引更新采用可重试机制和一致性校验；避免重复、越权、旧版本覆盖用户修正。
- 创建提醒、取消提醒、更新记忆、删除记忆时，数据源与检索结果应最终保持一致且可验证。
- 用户能够查看、纠正、删除自己授权保存的记忆，且有合理的索引清理策略与明确的隐私说明。

### 4.4 必须通过的跨会话例子

会话 A：“明天带**绿色 U 盘，不是银色的**。”

会话 B：“明天还要带**雨伞**。”

会话 C（新建、无近期上下文）：“我明天要带哪些东西？”

预期：在授权允许且两项均已持久化前提下，同时召回“绿色 U 盘（非银色）”“雨伞”，并能分别打开其来源事件/提醒详情。不得只记住一个、乱编额外物品或错误宣称已设置提醒。

## 5. P1：早、中、晚三时段自动回忆

### 5.1 基本定位

用户希望：只要某时段内有聊天，就将该时段中**最值得回忆的真实事件**作为候选，在固定时刻自动生成一张回忆图；用户不必每次点击“生成”，也不需要即时弹窗打断。当下次打开“我的回忆”时，可以自然发现这张图片。若没有值得纪念的事件，不强行生成。

原始照片、聊天原件与 AI 生成图必须区分；AI 图不能冒充用户现场拍摄的照片。初次启用自动生成需适当、清楚的授权，随后在设置中可开关、修改时段与执行时间。

### 5.2 事件提取与打分

每个时间窗内收集**已写入且授权用于回忆生成**的事件记忆，不直接凭 LLM 当前上下文生图。

评分建议维度：

- 事件独特性与重要性（首次、纪念日、特殊经历）。
- 情绪/主观意义（仅依赖用户实际表达，不自作推断）。
- 事件完整性（时间、行为、场景等信息是否足以真实还原）。
- 与该时段主题的代表性、多轮对话中的反复提及程度。
- 去重和安全/隐私适宜性。

每窗最多选一个主要事件；若没有足够质量或许可，则生成 0 张。排序需有可调权重、日志与回测样例，并保留选择依据。用户可以纠正事实、标记“值得留念”或“不要生成”。

### 5.3 调度与归属

- 时间窗必须可配置。初版可将 **05:00–11:00 / 11:00–17:00 / 17:00–23:00** 作为**提议**，其余时间归属、夜间跨日边界请在产品配置中明确，不得默默漏记。
- 用户此前指定了早段示例 **11:00** 出图；午段与晚段具体执行时刻应产品化配置，暂可使用 17:00 与 23:00 作为待确认默认候选，不能当作用户已确定的要求。
- 按用户设置的 IANA 时区计算，区分“聊天发生时间”“事件时间”“生成时间”。
- 支持任务去重、幂等键、队列/定时器、失败重试、超时、取消与重新生成；服务重启后不重复发送通知、不重复插入图片。
- **默认静默写入“我的回忆”**，不因生成成功而额外推送打断用户；有通知偏好时才额外通知。
- 回忆详情可查看：图片、文字事件说明、所属时间窗、来源记忆、真实/生成标签、纠错入口。权限与源数据一致。
- 如果生图提供商不可用，保留候选记忆并呈现文字回忆或待生成状态；不得伪造成功图片。

### 5.4 防止内容编造

- 提示词只能依据真实已持久化事件构建；不新增聊天未提供的具体人物身份、服装、建筑、天气、交通等关键事实。
- 用户肖像、生物特征和敏感事实须遵守授权，不擅自从历史数据推断写入画面。
- 明确显示“AI 生成回忆画面”；真实照片保持原样、单独标识。
- 支持撤回生成许可及删除衍生图，避免后台继续用已删除事件生成内容。

## 6. P1：统一数据关联与页面可达性

请根据仓库现有架构建立或核对以下关联（字段可映射到现有结构）：

`user_id` ← `conversation_id` ← `message_id`  
`message_id` → `memory_id` / `event_id` → `moment_id`  
`message_id` → `reminder_id` → `provider_task_id`

要求：

- 卡片跳转使用**后端真实返回的稳定 ID**，不能用 UI 数组下标或用户输入的模糊文本匹配。
- 聊天、提醒列表、记忆列表、回忆相册读取相同实体的真实状态；必要时对读缓存做失效处理。
- 有独立的“查看详情”“查看原对话”操作，跳转目标必须不同且清楚。
- 页面可链接、可刷新、可回退；当事件被取消/删除，相关详情有明确状态而不是死链接。
- 记录简洁可审计的事件日志（创建草稿、补全、成功保存、取消、索引、检索命中、回忆生成等），不要保存密钥或过量隐私数据。

## 8. 分阶段执行与每阶段交付

### 阶段 A：只读审计与根因定位（先执行）

输出：
- `docs/development-log/V023_BASELINE_AUDIT.md`
- `docs/development-log/V023_ROOT_CAUSE_MAP.md`
- 实际组件、路由、API、数据库实体、外部提供商的关系图
- 已证实根因列表 + 证据（文件路径/函数/调用/数据库检查/浏览器复现），以及暂未证实的问题。

在不修改源码、不写真实数据的条件下复现“聊天→提醒/记忆/回忆页面不可达”、跨会话记忆丢失、错误表单出现的具体步骤；若不能复现，记录环境与差异，不编造修复。

### 阶段 B：修复导航和提醒体验（P0）

- 先打通聊天到业务详情的直接导航，再实现已知字段预填与快捷时间选项。
- 核查时间解析、IANA 时区、事务、幂等、取消同步。
- 每一个修复要有明确前后对比与浏览器实际录像/截图。
- 保持 V0.2.2 已通过的所有功能不回退。

### 阶段 C：跨会话记忆闭环（P0）

- 先跑真实存储与检索的链路审计，再做局部补齐。
- 基于用户 ID 跨会话检索，保证来源可查看、授权与跨账号隔离。
- 针对“绿色 U 盘/雨伞”多事实查询写服务端、前端与真实 LLM 联调测试。

### 阶段 D：三时段回忆（P1）

- 在记忆持久化稳定后才实现事件精选、任务调度和生图。
- 首先用**明确标识的模拟聊天**验证选择算法，然后在隔离测试账号中验证真实生图和页面入口。
- 不许以生成图片数量为唯一 KPI，重点验证事件选择正确性和无内容编造。

### 阶段 E：端到端验收与交付

- 自动化测试 + 真实浏览器 + 真实 LLM + 真实数据库 + 真实提醒链路；各自说明采用 Mock 还是真实环境。
- 原始数据前后对比、无授权变更、接口安全、手机通知端结果分开验收。
- 汇总 `PASS / PARTIAL / BLOCKED / FAIL / UNKNOWN`，禁止未经证明写 PASS。
