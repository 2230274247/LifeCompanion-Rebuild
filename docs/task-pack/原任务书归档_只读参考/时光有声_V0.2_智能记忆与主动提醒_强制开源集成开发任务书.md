### 痛点 A：聊天、记忆、回忆的概念和链路混乱

1. 聊天消息必须完整、可靠地保存（遵循用户授权和删除策略）；不能把压缩后的记忆覆盖原始聊天。
2. **记忆是对聊天中的事实、人物、关系、偏好、事件、变化的可溯源压缩表达**，同一事实跨会话反复出现时合并或补充，不制造重复记忆；相关事实能够建立联系，并能记录时间变化。
3. 记忆权重不等于原词出现次数。系统同时维护“事实可信度/强度”和“回忆价值”，二者必须分离。
4. **回忆是从特定时间段内、已具备记忆证据的候选事件中筛选并呈现的内容**。回忆不能独立生成未经确认的真实经历；应能追溯到 memory_id、event_id 和 source_message_ids。
5. 后端采用图谱记忆：同一“初创公司”概念可被多家不同公司引用，但不会将这些公司误判为同一实体。人物、公司、事件、关系随时间发生变化时，要保留历史。
6. 已有早、中、晚定时回忆/生图产品策略应保持兼容；无有效候选事件时可以不生成，避免凑数量。AI 生成图必须有 AI 创作标记，不伪装为真实照片。

### 痛点 B：提醒依赖关键词，缺少主动建议

1. 用户不说“提醒我”，只要自然语言表达出明确或潜在的未来行动、日程或待办，系统都应能够识别并按置信度提出建议。
2. **提出建议 ≠ 创建提醒**。系统以自然语言建议卡片询问是否需要；用户点击后进入现有提醒编辑弹窗；只有用户明确确认且服务端保存成功，才创建真正的提醒。
3. 能处理“明天九点去医院”“周五下午去见朋友”“改到下周二”“不用提醒我”“不是我，是我女儿要去”等否定、转述、撤销、改期、指代和时间歧义。
4. 事件时间（event_time）与提醒时间（remind_at）必须区分，时区以用户设置为准；时间缺失或模糊时不得虚构确切提醒时间。
5. 提醒必须在应用/浏览器刷新、后端重启后仍可恢复；通知发送状态与真实送达状态不得混淆。

### 必须明确区分的技术职责

- **MySQL 是原始业务事实系统**：原始消息、确认的日程、删除与授权状态是业务记录；Graphiti/Neo4j、向量索引是基于授权数据生成的派生索引。
- **LangMem 管“提取、合并和压缩记忆”**：输出规范化的候选事实/事件/偏好和变更动作，由统一业务仓储写入；Graphiti 接受已审查的事件/事实进行关系索引。不允许双方平行生成互不一致的用户事实主库。
- **Laya 负责判别，不负责生成故事**：分类是否有提醒意图、事件纪念价值分布、候选分类等。它的原始概率**不等同于可靠的真实世界置信度**；需在中文业务样本上校准和设置阈值。
- **Qwen 本地小模型负责语义理解和补全结构，而不是替用户做不可逆决定**：对不明确姓名、公司、关系、日期必须允许 unknown/ask_user。
- **LangGraph 负责确认和恢复**：未经用户点击确认，不能实际创建提醒；图节点可能在恢复时重新运行，所有写操作必须幂等。
- **APScheduler 只负责到时执行和任务排程**：是否发出通知，由提醒状态及用户授权决定；对外推送渠道根据现有项目审计结果选择，绝不把“任务入队”当作“送达”。

### 项目升级前必须核实上游 API 版本

Graphiti、LangMem、LangGraph、APScheduler 的 API 均可能发生变化。首先阅读对应官方 README、文档与锁定的版本；给出兼容矩阵和依赖锁定。发现冲突时必须保留指定技术，采用适配层/分服务隔离解决；确实无法运行时写 `BLOCKED` 并说明原始错误，不准悄悄改为其他第三方方案。

## 3. 数据模型：聊天、记忆、事件、实体、回忆严格分层

### 3.1 五层概念

1. `chat_messages`：用户和 AI 的原始消息、会话、时间、来源和发送状态；原文保留，仅按授权保留期限/删除策略处理。
2. `memory_items`：归一化的用户事实、偏好、知识、长期目标，具备 evidence、confidence、status 和 revision。
3. `memory_events`：带时间和参与者的经历，例如“遇到旧友”“被邀请加入公司”“开始新项目”。
4. `graph_entities / graph_relations`：Graphiti + Neo4j 中的实体和关系索引；保留 Graphiti episode 与 MySQL source IDs 的映射。
5. `recollections`：由某一时间窗内的记忆事件生成的精选呈现，和原始消息、memory_item、event 绑定。

其中 `memory_items`、`memory_events` 是 MySQL 中**归一化业务记录和来源引用**，图谱不自行取得凌驾于主数据之上的写权限。

### 3.2 推荐新增实体（准确字段由 P0 结合 ORM 设计）

| 结构 | 最少字段 |
|---|---|
| `memory_items` | id、user_id、kind、canonical_content、status、confidence、strength、valid_from、valid_to、last_confirmed_at、version、created_at、updated_at |
| `memory_evidence` | id、user_id、memory_id、message_id、event_id、evidence_role（support/correct/contradict）、created_at |
| `memory_events` | id、user_id、event_type、title、occurred_at_start/end、observed_at、participants、location（可空）、source_confidence、status、created_at |
| `entity_registry` | id、user_id、entity_type、canonical_name、aliases、external_ref（可空）、resolution_status、created_at |
| `memory_graph_sync` | user_id、memory_id/event_id、graph_episode_id、sync_state、last_attempt_at、error、version |
| `memory_change_log` | id、user_id、target_type/id、before_version、after_version、action、reason、source_message_ids、created_at |
| `recollection_candidates` | id、user_id、window_start/end、event_id、memory_ids、features_json、model_scores_json、decision、reason、judge_model_version |
| `recollections` | id、user_id、candidate_id、event_id、memory_ids、source_message_ids、text、image_asset_id、ai_generated、status、created_at |

必须有用户域隔离的唯一约束、时间索引和幂等键。实际迁移采用现有 Alembic/迁移体系，不得创建第二套并行迁移机制。

### 3.3 实体、概念和关系设计

- `Person` 代表具体人物；`Organization` 代表具体公司；`OrganizationType` 代表分类概念（如“初创公司”）；`Event` 代表经历；`Place` 等按实际需要扩展。
- 区分实体：`朋友甲` ≠ `朋友乙`，`公司A` ≠ `公司B`；即使都属于 `初创公司`，也只能共享概念，不得合并实体。
- 常见边：`KNOWS`、`MET_AT`、`WORKS_AT`、`INVITED_TO_JOIN`、`MEMBER_OF_CATEGORY`、`PARTICIPATED_IN`。
- 关系上必须有 `source_message_ids`、`fact_id`、`observed_at`、`valid_from/valid_to`、`confidence`、`user_id/namespace`。如果部分属性由 Graphiti 内部表达，通过映射表与查询层保证同等追溯能力。
- 事实不确定时允许 `provisional_entity`，不能因为称呼相似就把“小王”和“王总”合并。
- “我们的公司发展很好”在未确定“我们的公司”是哪家时，必须标记含歧义，不得误建立用户入职/持股事实。
- “朋友邀请加入”≠“用户已经加入”；“曾经就职”≠“当前就职”。
- 修改后旧关系不是简单物理删除：需根据事实有效性维护历史，但用户明确删除其个人信息时应依授权删除派生索引。

### 3.4 记忆重复与强度更新

同一事实出现多次时执行：

`新消息 → 事件/事实抽取 → 用户域内语义检索 → 实体归一化 → 比对冲突 → CREATE / MERGE / UPDATE / MARK_HISTORICAL / ASK_CONFIRMATION → 保存 evidence → Graphiti episode/关系同步`。

强度不只由关键词频率决定。至少区分：

- `source_count`：独立来源数；同一条消息、同一会话机械复述不能无限累加；
- `explicit_importance`：用户明确说“这很重要”“请记住”等；
- `recency`：时间新近程度；
- `durability`：信息是稳定偏好还是临时情况；
- `confidence`：抽取/来源可信度；
- `contradictions`：是否被纠正或否定；
- `memory_strength`：可解释的归一化分值；
- `recollection_score`：**另一个独立评分**，不能直接等于 `memory_strength`。

先采用透明、可审计的权重初值+去重规则，并在评测集上拟合，不得硬编码“出现五次=永远记住”。重复信息只更新版本、引用和可信度；真正新增条件、关系或事件时创建新的事实/关系。

### 3.5 数据与图谱一致性

- 采用 transaction/outbox 或等效可恢复事件机制：MySQL 成功后，异步写入图谱；失败状态可重试，不让聊天发送因此丢消息。
- 图谱任务幂等：同一 message/event 重试不能产生重复实体或关系。
- Neo4j 不可用时，聊天不应整体中断；状态显示 `graph_sync_pending`，恢复后重建。
- 支持按 `user_id` 完整重建图谱、按时间窗增量重放、核验 MySQL 与 Graphiti 索引数量/引用一致性。
- 用户删除聊天或记忆时，按依赖链失效相应关联，避免缓存与生成回忆继续引用已删除内容。

## 4. 真正运行 LangMem + Graphiti（不仅“装上去”）

### 4.1 LangMem 接入点

- 聊天消息成功持久化后，向后台队列登记 `memory_ingestion`；避免网络请求结束之前把 AI 推断当作已提交事实。
- LangMem 使用已锁定版本的 memory manager/store manager，实际读取用户已有归一化 memory（而不是无记忆地每次新建）。
- 提取结果统一转为 Pydantic 类型：`MemoryProposal`、`FactAssertion`、`MemoryMutation`、`EntityMention`、`EventProposal`。
- 所有变更记录操作类型（create/merge/update/historical/reject）与依据，完成后将事件提交给 Graphiti；不能使用没有持久化的 `InMemoryStore` 作为正式长期存储。
- 不强制每条闲聊都产生长期记忆，不为了累计数量制造事实。

### 4.2 Graphiti 接入点

- 使用 Neo4j 的独立 Docker 服务与持久卷；初始化用户/权限，避免将 Neo4j 浏览器、Bolt 端口暴露公网。
- 根据锁定的 Graphiti 版本写 Python 适配器，使用其实际的 `add_episode`、`search` 或相应 API，禁止伪造兼容。
- 每个 Graphiti episode 映射来源 ID 和用户 namespace/group（以 Graphiti 版本支持为准），避免跨用户关联。
- LLM/Embedding 客户端优先接入本地 Qwen 服务；如遇 Graphiti 对特定模型的 JSON/schema 兼容问题，用官方支持适配器与结构化验证，保留完整失败日志。
- 能以真实 Neo4j Cypher 查询验证：
  - 朋友甲和朋友乙都属于“在初创公司工作的朋友”；
  - 两人实际分别就职不同公司；
  - 某人改换雇主后，当前关系与历史关系能被区别。
- 生产部署不假定 Graphiti/Neo4j 内部结构不变；通过独立 adapter 层隔离第三方 API。

### 4.3 记忆查询逻辑

常见问题：

- “我最近提到过谁在创业？” → 图查询 + 时间过滤 + 原始证据；
- “小王现在在哪上班？” → 当前关系，必要时说明信息截至哪天；
- “我什么时候第一次提到这个朋友？” → 追溯消息首次出现时间；
- “我们有几个在初创公司工作的朋友？” → distinct 人物节点，不能数概念节点或重复消息；
- “这两个人是否同事？” → 比较公司实体 ID 和关系有效期，不能依靠自然语言相似度。

所有面向用户的回忆/知识问答要允许“不确定”“还没提到”“需要确认”，不得编造姓名、公司、入职或关系。

## 5. 强制本地部署 Laya（Jev 的开源替代）

### 5.1 选型结论

- **必选生产原型**：`convaiinnovations/laya-multilingual` 官方开放权重 + Laya 上游 Python/HTTP serving，优先支持中文。
- **强制参照仓库**：`NandhaKishorM/laya`；使用其官方 API、Docker 或 `laya-serve` 文档，锁定代码 commit 与模型 revision。
- **中文优化研究参考（不作为现成权重）**：`yanqiangmiffy/chinese-laya`；该仓库分享中文微调方案与评测记录，**不保证附带可直接部署的训练权重**。不得误写“已引入中文 Laya 微调成品模型”。
- 如多语言 Laya 在真实中文口语表现不达标：仍保留已实装的 Laya 服务，使用既有本地 Qwen 复核/升级，并记录 Laya 在当前任务中的准确率不足；可以在积累人工标注样本后复现中文微调，不能用少量 demo 证明模型已校准。

### 5.2 必须具备本地服务能力

1. 完整下载/缓存模型权重，显式记录模型名、revision、SHA（若可用）、许可证、大小、推理依赖；
2. 独立服务容器或进程，可在 CPU/GPU 上运行；服务启动与健康检查可被其他应用调用；
3. REST API 实际调用，至少有意图 Choice、回忆 Score、是否需要补充确认 Noul 的真实返回结果；
4. 日志保留模型版本、请求耗时、失败类型、判别类别，不记录未授权原始敏感内容；
5. 不允许把权重随 Git commit 上传；提供自动下载、离线导入和目录挂载两种方式；
6. HTTP 服务设置独立内部密钥/网络限制，不能把推理端口直接裸露公网；
7. 在本机和 Docker 网络环境两种模式进行连接测试，提供 Compose 环境配置说明。

### 5.3 Laya 的输入任务设计（先做业务标注集）

**提醒意图 Choice**（示例枚举，需要按现有产品最终确定）：

- `NO_ACTION`：闲聊，没有待办/提醒建议；
- `FUTURE_EVENT`：讨论未来日程，可能需要建议；
- `EXPLICIT_REMINDER`：明确希望被提醒；
- `TASK_INTENT`：未来要完成的事项但没有具体时间；
- `EDIT_REMINDER`：改动已存在的事项；
- `CANCEL_REMINDER`：明确取消提醒；
- `QUOTED_THIRD_PARTY`：转述他人的计划，默认不创建用户自己的提醒；
- `UNCERTAIN`：语义不足，需更多上下文。

**回忆评分 Score**：个人意义、情绪显著性、事件独特度、可回溯性、适合生成回忆的程度等；具体量表与阈值先配置后校准。

**是否有必要追问 Noul**：事件时间是否足够明确？涉及人员是否明确？此时直接建议提醒是否合适？

不得将 Laya 输出的概率当作事实真实性的数学保证。需要做概率校准、ECE/Brier、分组准确率和低置信度升级处理。

## 6. 强制本地 Qwen 结构化理解与 Embedding

### 6.1 Qwen3-4B-Instruct-2507

- 作为**本地复杂中文提取/纠错/指代消歧服务**，可选择经核验的 Ollama、vLLM 或 Transformers 推理方式，但必须暴露稳定的内部 API；所选方式与版本在 README 中标注。
- 预设 JSON Schema，输出 `people`、`organizations`、`events`、`facts`、`references`、`temporal_constraints`、`ambiguities`、`evidence_spans`；后端用 Pydantic 校验。
- 无法确认“老朋友是谁”“我们的公司指哪一家”时返回 `unknown` 或建立待确认的临时引用。
- 对口语化中文、错别字、代词、省略信息、事件改期必须包含专项回归测试。
- 聊天仍由现有 DeepSeek 路由，不允许未经批准替换聊天主模型或把聊天密钥暴露前端。
- 模型执行超时要有可恢复任务状态，不能导致原始消息丢失。

### 6.2 Qwen3-Embedding-0.6B

- 本地向量化用于候选召回、相似记忆检索和去重；固化模型 revision、output dimension、归一化策略、prompt/instruction 模板与索引版本。
- 需要确立一个可查询向量存储后端：优先复用项目已有 Qdrant/向量方案；若现有技术栈没有，则按 P0 评估后新增 Qdrant（开放部署），**不得仅依赖 Python 进程内数组作为长期索引**。
- 通过 `user_id` 命名空间隔离、向量删除/重建与 MySQL memory ID 关联。
- 向量相似度只能召回候选，**不能仅凭相似度确认“同一朋友”或“同一公司”**；还需结构化实体核验。

### 6.3 硬件和迁移

- 首先只读盘点 RAM、VRAM；记录 Laya、4B、Embedding 是否可以同时装入当前机器，测峰值资源与延迟。
- 资源不足时优先合理拆分容器、串行执行、限制并发或在内网其他节点部署；必须有 Docker Compose profiles（或等效配置）支持单机和分布式拓扑。
- 在资源受限机器上允许服务因硬件不足保持 `BLOCKED_RESOURCE`，**但不允许伪装为本地推理成功**；所有业务测试应区分 mock contract test 与真实模型 integration test。
- 配置统一 `DECISION_BASE_URL`、`EXTRACTION_BASE_URL`、`EMBEDDING_BASE_URL`、`GRAPH_DB_URI`，不能在源码写死 `localhost`、`127.0.0.1` 或 H 盘路径；客户端通过服务发现/配置访问。

## 7. 智能回忆：时间窗筛选 + 轻量判别 + 可信生成

### 7.1 运行链路

`聊天入库 → LangMem 记忆整理 → Graphiti 图谱更新 → 事件进入候选集 → 在时间窗内检索并聚合 → Laya 多维评分 → Qwen 仅在低置信度/复杂事件时复核 → 规则与授权检查 → 确认候选有真实 memory/event/evidence → 回忆文案 → 可选图片生成 → 回忆库发布`。

“时光有声”原先设定固定早/中/晚时间窗自动生成回忆（如早上 11:00 晨间汇总）；**必须先审计现有时间窗口和调度配置**，不可写死新的时间段覆盖已有配置。每个窗口的起止边界和时区明确写入任务记录。无聊天/无有效事件时跳过，不制造“今天你一定做了什么”。

### 7.2 评分/选择规则

- `memory_strength`：长期记忆重要程度，来自已保存记忆的结构化证据；
- `recollection_score`：该时间窗内该事件的纪念价值，来自 Laya 的情绪、意义、独特性、完整性等维度及业务特征；
- `quality_gate`：真实性依据、时间匹配、重复程度、授权状态、可能造成误解的生成内容；
- `diversity`：一天有多条候选时避免三张图都围绕同一件事；
- `candidate_dedupe`：同一事件跨窗口反复出现，默认不重复发布，除非出现有意义的新进展。

**禁止**因情绪强烈就自动把私密、敏感或可能不适宜展示的事情转为“惊喜生图”。对于健康、家人、个人隐私等内容应尊重用户的相关授权和回忆生成设置，提供人工排除和删除控制。

### 7.3 可追溯性

每个发布回忆至少保留：`user_id / window / event_id / memory_ids / source_message_ids / scoring_version / generative_model_version / created_at / ai_generated`。用户可以查看“这段回忆来自哪些聊天”，但要依据其账号权限控制，不泄露他人数据。删除源消息或撤销授权后，相关派生回忆要进入重新评估/失效处理流程。

### 7.4 人机交互约束

- 不新建第二套回忆首页；复用既有回忆列表/卡片/相册/时间轴、图片展示和生成状态。
- 不为了接新功能大改 V0.2 的 Ember 配色、字号、动效与路由；新增仅必要的后台调试页或管理统计。
- 不能将“AI 回忆图片”描述为真实摄影记录；无法保证肖像真实复现时必须避免编造具体细节。
- 允许后台记录为什么某个窗口被跳过、候选为什么未过阈值，便于研发验收而非必须展示给用户。

## 8. 智能提醒：意图识别 → 轻量询问 → 用户编辑 → 确认执行

### 8.1 真实聊天触发

在现有每次成功发送用户消息之后，利用必要的近期对话上下文调用**本地 Laya**，识别是否有未来事项、任务、改期、取消、明确提醒需求。只取当前用户授权的最小必要上下文，异步执行且不阻塞主聊天。

如出现未来事件候选：

- 高置信度且信息足够：在聊天流中展示非侵入式建议卡片“需要我帮你设个提醒吗？”；
- 中等或信息不足：提问必要的单个关键信息或给可编辑建议，不随意猜时间；
- 低置信度或否定/转述：不主动打扰；
- 明确“提醒我”：可以更主动引导，但仍须用户确认具体时间和保存；
- 修改已有提醒：先解析目标提醒、展示差异并获得确认；
- 取消提醒：必须选中明确对象并由用户确认（或沿用现有授权的明确确认规则）。

避免连续多次骚扰：按用户、事件指纹和时间窗口做去重及冷却；用户已拒绝的相同事件不重复弹窗；可在设置中关闭主动建议。建议卡片应能“稍后再说/不再提示这件事”。

### 8.2 前端最小改造

- 聊天消息组件增加 `ReminderSuggestionCard`（命名以现有结构为准），与聊天记录一起正确恢复；
- 卡片有 `建议中 / 可创建 / 已忽略 / 编辑中 / 保存中 / 已保存 / 保存失败` 状态；
- 点击“创建/设置提醒”打开原生 V0.2 提醒编辑弹窗，自动预填可确认字段；
- 弹窗必须有：标题、事件日期/时间、提醒日期/时间、提前提醒、时区或时区提示、保存/取消；与现有设计系统一致；
- 在服务端确认保存前不得显示“提醒已创建”；失败后保留用户编辑内容，允许重试；
- 若前端刷新、断网或用户离开后再打开，建议、流程和已保存任务应能从服务端恢复。

### 8.3 LangGraph 的真实用法

建议状态：

`DETECTED → PROPOSED → WAITING_USER_CONFIRMATION → EDITING → VALIDATING → COMMITTED → SCHEDULED → DUE → DELIVERY_ATTEMPTED → DELIVERED / FAILED`；

拒绝路径：`PROPOSED → DISMISSED`；修改路径：`COMMITTED → CHANGE_PROPOSED → WAITING_USER_CONFIRMATION → UPDATED`；取消同理。

- 采用持久化 checkpointer + 稳定 `thread_id`，在等待用户选择时执行真实 interrupt/resume，重启后可以继续。
- 所有状态写入具备幂等键；**LangGraph interrupt 所在节点恢复时可能重新执行之前的代码**，因此不能在 interrupt 前做不可幂等的插入/发通知。
- 未经确认的 proposal 与正式 reminder 是两条不同记录；拒绝/关闭弹窗不留下待发送任务。
- 错误恢复时不能重复创建提醒或重复投递通知。

### 8.4 时间解析与计划语义

必须支持时区、相对日期、年份跨越、凌晨、模糊时间、“九点去医院”与“九点出门”等区分。

- “明天早上九点去医院”：`event_at` 可能是预约到院时间，`remind_at` 仍待用户确认；
- “明天九点出门”：事件是出门，提前多少分钟提醒需确认或采用用户已授权偏好；
- “周五下午见朋友”：时间粒度不足，必须确认几点；
- “后天把材料交给老师”：可提出待办，缺具体截止时刻时不虚构精确时间；
- “下周二改成周四”：定位正确的原始日程后询问确认；
- “不是我，是朋友明天要开会”：不能自动归为用户待办。

如已有地址/交通/天气能力可在用户允许后辅助建议出门时间；**不要将交通耗时、天气数据凭模型猜测写入正式提醒**。

### 8.5 实际调度与通知

- APScheduler 使用独立持久服务运行；按官方锁定版本选择持久数据存储。Web API 进程不应各自启动同一份 scheduler。
- MySQL 提醒记录保留统一状态；任务执行使用幂等 `delivery_key`。重启后应能恢复将到期但未完成的提醒，已取消提醒绝不发送。
- 真正发送渠道以 P0 审计已有能力为准，优先复用已有 Web Push/站内通知；浏览器关闭后能否送达必须在目标浏览器真实验证。
- 严格区分 `created / scheduled / attempted / provider_accepted / delivered_confirmed / failed / unknown`。无法收到回执时只能报“已提交/已尝试”，不得假写“已送达”。
- 未经浏览器通知授权，不能假定弹窗通知必能送达；站内通知和系统推送的能力边界须在产品里说明。

## 10. 测试集、评测指标和强制验收门槛

### 10.1 自动生成隔离的合成数据

创建测试环境种子脚本（不能操作真实用户数据库）：

- 至少 **8 个隔离的合成用户**，用于验证跨用户安全隔离；
- 每个测试用户有多轮跨天对话：重复事实、名字别称、关系变化、两家公司同类别、时间顺序混乱；
- 至少 **200 条标注的意图判断样本**（涵盖日程、待办、否定、转述、修改、取消、中文口语）；
- 至少 **100 组记忆合并/冲突/关系推理样本**；
- 至少 **100 个回忆候选事件**（含高价值、低价值、重复、无聊天、隐私授权、模糊与无证据）；
- 包含真实错误模式的测试样本：错别字、日期跨月/年、指代不明、两个朋友在不同公司、轻微情绪但意义重大、强烈情绪但不应生图。

所有生成数据必须标记 `synthetic=true`，具备固定随机种子、清晰标注、可重复运行；不能宣称合成样本代表真实老年用户全分布。提供人工抽检入口，至少对一批样本进行人工复核。

### 10.2 核心指标（验收目标，非现成已达到的性能）

| 能力 | 验收目标 | 检验方式 |
|---|---|---|
| 原始消息完整性 | 成功提交消息 100% 可追溯、重试不重复 | MySQL 计数、唯一键、断网/重启测试 |
| 记忆去重 | 标注的同一事实合并准确率 ≥90%，不允许靠删除源消息达标 | 100 组标注样本、错误案例清单 |
| 实体消歧 | 测试集不同公司误合并为同一公司 **0 例**；不同人物误合并 **0 例** | 指定高风险 fixture 逐项断言 |
| 时序事实 | 指定改期/跳槽 fixture 100% 正确区分历史与当前 | Neo4j + MySQL 查询证据 |
| 来源可追溯 | 测试回忆和事实 100% 有有效 source_message_ids | 数据完整性检查 |
| 提醒意图 | 样本集宏平均 F1 ≥0.85；“非明确提醒但有日程”召回率 ≥0.90 | 锁定标签集，计算精确率/召回率/F1、混淆矩阵 |
| 误触发控制 | 否定/转述/拒绝的高风险样本不能误建提醒 | 高风险 fixture 全通过 |
| 未确认创建 | **0 例**未经用户明确确认即建立正式提醒 | API、DB、E2E 自动断言 |
| 任务幂等 | 重复提交、刷新、重启不造成重复提醒/通知 | 并发 + 重放测试 |
| 回忆筛选 | 无证据/无授权候选 **0 例发布**；重复事件不得无故反复发布 | 回忆候选/回忆成品审计 |
| Laya 本地真实性 | 实际加载本地权重并返回 typed decisions；无网络到 Jev 的调用 | 服务日志、进程/权重证明、离线/受控网络测试 |
| 后端迁移 | Windows 开发配置与 Ubuntu Compose 配置可运行同一套 API Contract | Docker、配置对照和实际 smoke test |
| 跨用户隔离 | **0 例**交叉访问、交叉记忆召回或数据泄漏 | 至少8用户混合并行测试 |
| 用户删除与纠正 | 删除/纠正能传播至派生索引与回忆引用，不留下可查的错误事实 | 删除后检索及重建测试 |

对 F1 这类统计指标提供样本数和置信区间（可使用 case-level bootstrap），按明确日期划分训练/校准/测试；阈值只能在验证/校准集上调整，**不能看了最终测试答案再改阈值造达标**。

硬性安全/数据完整性门槛（如未确认创建、跨用户泄漏、无证据的回忆发布）不允许通过降低阈值放宽。模型性能门槛若尚未达成，报告必须如实写 `PARTIAL`，继续给出混淆矩阵和改进方案；不能以几条演示成功替代测评。

### 10.3 必须包含的端到端验收场景

**A｜关系记忆跨天追踪（用户甲）**

- D1：“今天遇到了一个老朋友小王。” → 人物/相遇事件进入记忆与图谱；
- D3：“小王最近加入一家叫星火科技的初创公司，他还邀请我加入。” → 增量追加公司与邀请关系，不推断用户已加入；
- D5：“后来我真的加入了星火科技。” → 才新增用户加入关系；
- D8：“我们的团队最近发展不错。” → 可基于充分上下文关联到公司，但没有上下文时保留歧义；
- D10：“另一个朋友小李也去了初创公司，叫云帆智能。” → 两家公司是两个不同实体；
- D12：“小王离开星火科技，去了远山科技。” → 原雇佣关系成为历史，新关系为当前；
- 查询：“有几个朋友在初创公司？”“两人是否同事？”“小王现在在哪上班？”“最初是谁邀请我加入？”“哪些事实来自哪句话？”

**B｜重复记忆和纠错**

同义词、代词、不同表达重复提及同一事实 → 只有一份核心事实但有多条 evidence；随后“我记错了/其实不是这样” → 保留纠正记录，当前答复不重复引用错误事实。

**C｜自然语言提醒全闭环**

用户：“明天早上九点要去医院复查，得早点出门。” → 检测候选 → 聊天卡片建议 → 点设置提醒 → 弹窗预填并核对事件时间/提醒时间 → 用户明确保存 → MySQL 状态 `COMMITTED/SCHEDULED` → 到时真实渠道发送并记录投递结果。刷新、重启、取消、改期和重复点击全部覆盖。

**D｜非提醒句子的防骚扰**

“朋友说明天要开会”“昨天本来想去医院”“不用提醒我”“改天有空再去”“明天我可能想散步” → 不应该直接生成正式提醒；按需少量建议或不提示。

**E｜回忆筛选、生图与溯源**

同一时间窗既有“今早跑步完成第一次训练”又有日常无意义寒暄 → 选择有意义且证据充分的候选；无事件的时间窗跳过；回忆卡片能追溯事件与消息；生成图标注 AI 创作；删除相关源消息后索引/回忆正确失效。

**F｜混合故障**

Graphiti 连接中断、Laya 推理超时、LangGraph 流程暂停、APScheduler 重启、两次重复 webhook/请求、服务突然重启 → 原始消息不丢失、待处理任务可重试、无重复正式提醒、无跨用户串数据。

### 10.4 测试方式

- 单元测试：Pydantic schema、时间解析、权重计算、去重指纹、状态机；
- 集成测试：MySQL + Graphiti + Neo4j + LangMem + Laya + Qwen + Embedding 全部真实连通；
- 端到端：Playwright 驱动 V0.2 聊天、建议卡片、提醒弹窗、回忆详情，五种目标宽度（390、430、768、1440、1920）；
- 性能与稳定：模型冷启动/热请求延迟、并发队列、内存、显存、CPU、故障恢复；
- 用户隔离和授权：权限、删除、拒绝生图、禁止外发原文；
- 评测报告：按模型和功能分组统计，附失败样例、复现步骤、截图/录屏、服务端日志摘要（脱敏）。

## 12. 实施顺序、阶段门禁和真实交付

### 最终状态只能是

- `PASS`：所有强制开源服务已真实运行，端到端测试与安全门槛通过；
- `PARTIAL`：主要功能完成但仍有明确不达标项；
- `BLOCKED_RESOURCE`：资源不足，真模型未能启动；
- `BLOCKED_ACCESS`：仓库/权重/网络不可访问；
- `BLOCKED_COMPATIBILITY`：明确第三方版本冲突，附原始错误与最小复现；
- `FAIL`：核心数据完整性、隐私隔离、提醒安全门禁未通过。

**禁止“全部完成”但最终报告里写“未测试真模型、未检查数据库、只做了 UI 示例”。**
