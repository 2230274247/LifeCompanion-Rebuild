# 聊天与记忆链路检查：实际流程、召回限制与改进建议

检查日期：2026-11-08。方式：只读检查代码、容器挂载与服务连通性；以合成输入验证关键行为，运行相关既有测试。未修改业务代码，未读取真实用户聊天或数据库，未发送真实模型请求。

## 1. 结论与检查范围

现有系统已具备“保存用户消息 → 后台抽取 → 用户级记忆库 → 生成前检索并注入”的骨架，但不是通用、持续生效的语义记忆系统。用户描述的流程与实现最主要的差别是：**聊天回复和结构化记忆抽取是两条独立链路、可能是两次模型调用；检索不是每轮执行；抽取和召回均受大量固定规则限制。**

本次发现版本差异，不能只依赖当前工作树的旧文档：

- 本会话工作树基于 `e2711c7`，没有 `products/` 上游源码；其中的早期架构文档将长期记忆召回列为未完成。
- 本机运行中的 `lifecompanion-librechat`（3080）实际挂载主目录 `H:/AI For research institute/LifeCompanion-Rebuild/` 下较新的源码。
- 已从该容器读取实际加载的 `@librechat/api` 中 `withLifeMemory`、`queueLifeMemory`、`withLifeReminder` 函数，确认有记忆召回/入队代码，并与主目录对应源码核对。
- 本报告的新版后端分析来自主目录当前源码。因为检查时后端端口不可达，不能声称已核实正在运行的后端进程加载了哪一版代码。
- 本机另有 3083 等多个测试实例；以下运行探测针对已明确列出的本地实例，不能直接推广到公网部署。

下文源码位置均相对于上述主目录，使用“路径:行号”定位。它们不是本会话旧工作树内的同名文件。

## 2. 实际消息流程

### 2.1 回复链路：先读取旧记忆，再调用聊天模型

1. 用户发送文字，LibreChat 获取服务端认证的用户 ID、当前会话 ID 和消息 ID。
2. LibreChat 读取当前会话的历史消息，而非自动读取此用户的全部聊天窗口。`BaseClient.js:1290` 的 `loadHistory` 使用 `conversationId + user` 查询历史。
3. 构造模型输入时，`BaseClient.js:866` 调用 `withLifeMemory(messages, connection, currentText)`。
4. **先做固定词触发判断**。没有命中问号或“什么、哪些、多少、之前、记得、还记、以前、上次、除了、还有、刚才、这件事、这个”，立即跳过检索。
5. 命中后调用 `/internal/v1/knowledge/recall`，传用户 ID、当前文字、当前会话 ID、消息 ID。请求默认超时 3.5 秒。
6. life-core 通过 LibreChat 用户映射找到 `life_user_id`，从该用户全部有效 `memory_items` 中匹配，检查召回授权及敏感信息授权。
7. 返回最多 12 条记忆。会话 ID 用于记录本轮命中来源，**普通召回没有按当前会话过滤**。
8. 聊天端把记忆包装成“不可信证据、不能当指令”，附加到当前用户消息的模型输入副本；不把这段注入内容写回原始聊天。
9. LibreChat 将系统提示、当前会话历史、本次文字和命中的记忆交给所选云端模型，生成普通回复。

核心位置：

- `products/librechat-custom/api/app/clients/BaseClient.js:866`：记忆注入调用点。
- `products/librechat-custom/packages/api/src/memory/life.ts:16`：内部请求、条件缺失与超时。
- 同文件 `:132`：检索触发、最多 12 条、每条最多 500 字、注入与异常处理。
- `services/life-core/app/main.py:629`：用户映射、命中审计、返回契约。
- `services/life-core/app/memory.py:349`：用户级 active 记忆集合。
- 同文件 `:371`：召回算法。

**因此，同一窗口能回答某件事，不代表长期记忆保存或检索成功。** 它可能只是从当前窗口历史中看到原文。换窗口后，才真正依赖独立记忆库和上述检索链路。

### 2.2 整理链路：原文持久化后入队，另行抽取

用户消息在 LibreChat 持久化成功后，`BaseClient.js:1399` 调用 `queueLifeMemory`。入队与聊天回复不是一个共同提交的事务，也没有“本次抽取完成才能回答”的保证。

实际过程：

1. `queueLifeMemory` 只处理用户文字，最多取 4000 字；不把助手回复交给记忆抽取。
2. 调用 `/internal/v1/events/enqueue`，携带稳定消息 ID、用户 ID、会话 ID、原文与时间。
3. life-core 检查自动整理授权和敏感信息授权，按“用户 ID + 消息 ID”幂等入队。
4. 后台线程读取 SQLite `memory_jobs`，调用 `process_event(..., use_llm=True)`。
5. 先执行问题、否定、未来、假设等规则过滤。部分携带物品计划由规则直接识别。
6. 若启用模型且有对应 Key，单独请求记忆抽取模型；否则进入有限的规则抽取。后端支持 DeepSeek 和智谱配置，不能仅由聊天模型推断后台使用了哪个 Provider。
7. 抽取模型只返回一个候选：`stable_fact / life_event / future_plan / no_memory`，经 Pydantic 和来源子串检查等验证。
8. 稳定事实、计划写入 `memory_items`；生活事件还进入 `events` 并通过 Memos API 发布为私人条目。
9. 更新证据、修订、重要性、任务状态。任务正常结束后清空任务中的原文 payload。

这里有两个容易误判的状态：

- 入队返回 `accepted=true`：代表任务已进入队列，不代表已经保存记忆。
- 任务 `succeeded`：代表处理器正常返回；它也可能判定 `no_memory`，因此没有新增记忆。

关键位置：`packages/api/src/memory/life.ts:109`；后端 `main.py:235`、`:377`、`:577`；`memory.py:146`、`:195`、`:396`、`:408`。

### 2.3 不是“聊天模型顺带输出结构化记忆”

当前聊天提示词明确要求普通聊天不要输出结构化 JSON，并说明记忆抽取由独立后台完成，见 `products/librechat-custom/librechat.yaml:22`。

后台抽取模型收到的主要是**当前单条用户文字**，不是整段聊天、聊天模型回复和全部相关记忆。所以它对“他、那个项目、后来怎么样”等省略与指代的理解有限。

这种分离有合理目的：避免模型把自己编写的故事或推测再保存成用户事实。但它需要补充可靠的上下文和处理状态，才能达到自然的生活伙伴体验。

## 3. 数据存在哪里，哪些能被召回

| 层 | 主要内容 | 对跨窗口回复的作用 |
| --- | --- | --- |
| LibreChat MongoDB | 原始聊天及会话历史 | 默认读取当前会话，不等于搜索全部历史 |
| life-core SQLite `memory_items` | 已抽取的事实、事件、少量计划；有效状态、重要性等 | 当前普通记忆召回的主要数据源 |
| `memory_evidence` / `memory_revisions` | 来源消息、会话、日期、哈希、分类版本及修订 | 支持追溯、增强与撤回 |
| SQLite `events` + Memos | 已发布的私人生活事件 | 回忆展示与发布链路；普通召回不直接搜索 Memos 全库 |
| `moments` | 另行筛选、生成的图文回忆任务 | 影集链路，与普通聊天召回不是同一个筛选过程 |

因此：

- “在旧聊天里存在”不等于“已进入可召回记忆”。
- “在 Memos 页面存在”不等于“聊天会搜索到”。
- “没进入图文影集”不等于“不能作为文字记忆被召回”。
- LibreChat 自带 memory 在当前配置中是 `disabled: true`；这里讨论的是自研 life-core 记忆，不是原生 Memory 功能。

## 4. 已验证的问题

### A. 检索依赖固定触发词，不能自然地每轮关联记忆

位置：`packages/api/src/memory/life.ts:137`。

直接调用运行容器中真实加载的 `withLifeMemory`，将 fetch 换成合成返回值，未访问模型或真实记忆：

| 本次输入 | 检索请求次数 |
| --- | ---: |
| 最近压力很大 | 0 |
| 我又想喝点热饮了 | 0 |
| 你记得我爱喝什么吗 | 1 |
| 继续聊聊那个项目 | 0 |
| 继续聊聊这个项目 | 1 |

“那个”和“这个”只差一字，就会改变是否检索。这足以解释提示词依赖；修改云端聊天提示词无法让一个根本没被调用的检索步骤发生。

### B. 后端主要按中文两字重合检索，没有语义相似检索

位置：`memory.py:371`。

算法把问题和记忆去标点，拆成相邻两字的集合，计算交集大小；再对饮品、居住、带物品的少数词额外加分。按相关分优先、重要性次优排序，只保留有分的前 12 条。

本次用真实 `MemoryService.recall` 和合成记忆验证：

| 已保存记忆 | 查询 | 结果 |
| --- | --- | --- |
| 喜欢喝龙井茶 | 我爱喝什么 | 命中 |
| 喜欢喝龙井茶 | 我偏好的饮料是什么？ | 未命中 |
| 今天项目终于结束了 | 上次项目进展如何？ | 命中 |
| 今天项目终于结束了 | 那份工作完成得怎么样？ | 未命中 |

“饮料”和“喝茶”、“工作完成”和“项目结束”的语义关联没有被算法理解。上述问题都已包含触发词或问号，因此不是聊天端跳过检索所致。

提高 importance 也无法解决零相关分：没有匹配分的记忆根本不进入候选排序。

### C. 跨窗口检索范围已按用户共享，但指代解析仍局限于会话

`list_items` 与 `recall` 不按 conversation 过滤，所以不能把所有问题归因于“数据库把聊天窗口隔离了”。

但是 `memory.py:258` 的 `contextual_event` 只支持少数指令/“这个项目组”，只搜索同一会话，并要求恰好有一个可选生活事件。显式“加入回忆/记住刚才”的执行也主要使用当前窗口上一条用户消息，见 `life.ts:63` 和 `main.py:592`。

新窗口里的“继续说那件事”缺少实体、日期和主题补全；后端召回实际只用本次 `query` 匹配，没有利用传入 conversation ID 重写查询。它既不会自动遍历全部旧聊天，也没有通用的跨窗口指代连接。

### D. 很多内容在保存之前就被挡住

位置：`memory.py:146`、`:171`、`:195`。

- 稳定事实主要支持饮品偏好和居住信息；LLM 提示也只允许这两类稳定事实。
- 一条消息至多一个候选，不会把“生日、工作、喜好、当天事件”拆为多条独立记忆。
- 未来计划主要支持携带物品，不能概括为通用计划管理。
- 模型识别出的生活事件仍须通过旧事件词表验证，模型判断正确也可能被挡回。
- “希望、可能”等词会让整句先被拒绝，无法分开保留其中明确发生的部分。
- 用户原文最多传 4000 字，保留的规范文本最多 500 字；较长内容中的细节可能只留在聊天历史中。

本次规则分支合成复核：

| 输入 | 结果 |
| --- | --- |
| 我最喜欢喝无糖拿铁。 | `no_memory` |
| 我的生日是六月十五日。 | `no_memory` |
| 今天参加了年度学术会议。 | `no_memory` |

这三项直接复核的是未使用模型的规则路径。生日的通用稳定事实能力、生活事件词表限制在模型提示/校验路径中也存在；不能据此声称任意真实线上句子一定走了同一分支。

### E. 静默降级会掩盖记忆服务故障

本次探测结果：

- 3080 主聊天容器的 `LIFE_CORE_URL` 为 `http://host.docker.internal:8010`。
- 主机请求 `127.0.0.1:8010/health` 连接失败。
- 从该聊天容器连接 `host.docker.internal:8010`，返回 `ECONNREFUSED`。
- 3083 的备用聊天容器指向 8023；主机访问 `127.0.0.1:8023/health` 也连接失败。

`withLifeMemory` 请求失败直接返回原消息；`queueLifeMemory` 失败也吞掉异常。于是模型照常回答，但本轮可能既没有保存记忆，也没有召回记忆。

这证明检查时本地这两套入口的业务链路不可达；尚未检查服务停止原因、实际用户使用入口和公网部署，不据此断言过去所有问题都由停机引起。

另外，后台有 Key 时若模型失败会重试，最终失败，而不是自动切回规则。无 Key 的规则路径与有 Key 但请求失败，是两种不同情况。

### F. 还发现两项可能污染记忆的确定性问题

本次用实际规则函数复核：

1. `我现在不喜欢咖啡。` 被错误抽取为 `喜欢喝咖啡`。`memory.py:175` 对“不喜欢”的保护因包含“现在”而失效。这是规则分支的明确错误，不能直接推断模型分支也有同样输出。
2. 同一天的 `今天加入了甲项目组。` 与 `今天加入了乙项目组。` 得到相同 key：`event:2026-11-08:joined-project`。`memory.py:248` 未将项目身份写入 key，保存时会误并不同事件。

召回质量依赖保存内容正确；单独改检索算法不能消除这类源数据错误。

## 5. 当前权重和“加入回忆”的实际含义

### 5.1 文字记忆的重要性

`memory.py:273` 的保存逻辑：

- 新记忆通常 importance 为 0.5；原文包含“加入”时为 0.7。
- 对已有记忆，只有新增独立证据才 +0.08，上限 0.95。
- 独立证据要求内容哈希、日期、会话均不与既有证据相同；同一天换说法、同一窗口跨天、换窗口复制原文都不会增加权重。
- 显式加入生活回忆可把 importance 提到至少 0.9，见 `main.py:610`。
- confidence 与 importance 分开存储，不因反复提及自动一起增加。
- 主保存流程没有统一的 confidence 阈值；准入主要由分类规则、来源验证、授权和类型检查决定。

当前没有通用的时间衰减、实体关系建模或语义强化机制；召回主要用相关分，importance 只作后续排序因素。

### 5.2 生活事件发布

生活事件被主流程接收且有授权后，就会尝试发布到 PRIVATE Memos。它不是先积累很多次权重，再决定是否首次进入 Memos；稳定事实和未来计划则走不同分支。

### 5.3 图文回忆/影集

另一个 `Moments` 流程才负责定时挑选可生成图文的事件，见 `moments.py:183`、`:213`。

默认综合分为：

`0.5 × importance + 0.2 × uniqueness + 0.2 × emotion + 0.1 × completeness`

其中独特性、情绪、完整性也主要按关键词和长度判断。默认窗口为 11:00 / 17:00 / 23:00，默认门槛 0.4；仍需满足授权、有效生活事件、可配图、未被用过等条件。这是源码默认值，不代表已核对真实账号配置。

所以“能被聊天回想起来”“发布为文字事件”“选入图文影集”应作为三种状态分别理解和展示。

## 6. 与期望流程逐项对照

| 期望 | 当前实现 | 差距 |
| --- | --- | --- |
| 发送消息后自然关联过往信息 | 仅固定词触发召回 | 大量普通陈述不检索 |
| 找到曾经问过、提过的相关内容 | 检索已抽取 memory_items | 不搜索全部聊天，很多内容从未入库 |
| 理解换说法、跨窗口指代 | 两字重合 + 少量特例 | 无通用语义检索和查询补全 |
| 把记忆与本次输入一起发模型 | 已实现输入副本注入 | 取决于上游触发、服务可达和命中 |
| 模型回复同时给系统结构化记忆 | 独立后台处理原文，可能另调模型 | 不是一次回复双输出；抽取缺少上下文 |
| 保存并评估权重 | 已有类型、证据、修订、importance | 支持范围窄，规则仍粗糙 |
| 决定是否进入回忆 | 文字事件发布与图文筛选分开 | 需要明确产品概念和状态 |

## 7. 建议的修改顺序

### 第一阶段：先让链路状态可判断

1. 核对实际使用的入口、life-core 地址、端口、进程与数据库路径，使聊天、记忆整理和召回连接到同一套用户映射及数据。
2. 保留聊天可继续的行为，同时记录“未尝试检索 / 服务不可达 / 授权未开 / 无命中 / 已注入 / 抽取拒绝 / 模型失败 / 发布失败”等独立状态。用户界面给简洁状态，调试日志提供原因与耗时，不记录密钥。
3. 将队列处理成功和有效记忆已保存分开统计，确认新消息是否真正成为记忆。

这一步解决“到底是没有保存、没有查找，还是查了没找到”的诊断问题。

### 第二阶段：修复自然召回

1. 取消固定词作为唯一硬门槛。已授权用户每轮做一次有预算的本地候选检索，或用能覆盖普通陈述的路由机制；空结果正常返回，无需每轮调用大模型。
2. 把当前字符重合检索升级为关键词/实体/时间 + 向量语义召回，融合排序后取少量有效证据。对语义确实含糊的候选再考虑重排。
3. 结合当前窗口最近几轮用户内容、已确认主题和最近召回项，补全“那个项目、之前那个人”等指代。使用全用户范围检索，同时保留当前会话的相关性线索。
4. 给常用稳定事实建立独立、受预算限制的用户资料摘要；详细生活事件按需检索，避免所有长期信息都只能靠当轮关键词命中。
5. 排序综合相关性、时间有效性、当前状态、importance 与证据可靠性；时间语义明确时按事件日期筛选，不能只靠共享日期字样加分。

关键词检索能保留人名、地名、数字等精确信息，向量检索补足换说法。单纯取消触发门槛或单纯提高权重都不够。

### 第三阶段：修复“没被记住”和“记错了”

1. 修复否定极性错误和项目组 key 误合并。
2. 将单候选抽取扩展为多条有来源的事实/事件，支持人物关系、职业、生日、兴趣、目标等已明确授权的类型。
3. 给后台抽取提供有限的用户上下文及相关旧记忆，使其能判断新增、补充、纠正和冲突；保留助手内容不能直接成为用户事实的边界。
4. 保留来源子串、时间、授权与状态验证；把固定事件词表从最终否决门槛改成辅助信号，减少对真实事件的漏存。
5. 将事实、明确事件、未确定计划、问题讨论分别建模，不因一句包含“可能/希望”就丢弃所有已发生内容。
6. 历史未被抽取的聊天不会因新召回算法自动出现。若需要补齐，应另做按用户授权、可预览、幂等的历史抽取，不能直接把全部旧聊天倒进提示词。

### 第四阶段：用真实产品场景验收

建立同一用户多窗口、不同日期、不同说法的用例，同时检查：原始消息是否持久化、抽取内容是否正确、实际召回了哪些项、最终模型输入是否含证据、回复是否忠实。

至少包含：

- A 窗口保存生日/饮食偏好，B 窗口用同义句询问。
- 不带“记得、之前”和问号的普通陈述自然关联相关经历。
- 窗口切换后的明确主题与模糊指代分别处理；无法确定时澄清。
- 否定、更正、撤回、敏感授权、多用户隔离。
- 后台抽取尚未完成、模型失败、记忆服务不可达。
- 单消息多个事实、长消息、同一天多个不同项目事件。
