# 永久开发日志规范

每次独立开发任务必须新增一份中文 Markdown 日志，包括未完成、PARTIAL 或 BLOCKED 的任务。
禁止覆盖旧日志或仅在聊天、总 README 中汇报。

目录为 `docs/development-log/`，文件名为 `YYYY-MM-DD_HH-mm_任务名称_开发验收.md`；
重名追加序号。同步更新该目录的 README 索引。

每份日志必须包含：

1. 基础信息：任务、日期、开始结束时间、版本、分支、开发前 Git 状态、修改文件数量、是否提交及真实提交 Hash。
2. 目标与边界：原问题、计划、明确排除项。
3. 架构实现：组件、模块、API、数据模型、认证、兼容性、技术决策及理由。
4. 修改明细表：实际文件路径、修改内容、原因、影响范围。
5. 功能结果：完成、操作方法、既有功能影响、未完成部分。
6. 验收：环境、命令、时间、自动化/单元/API/浏览器/实际运行结果、失败与修复。
7. 前端证据：真实运行前后截图、多尺寸截图；录屏尽可能保存。附件放在对应日志的附件目录或项目 evidence 目录。
8. 遗留风险：功能、Bug、未验证、安全、性能、上线阻塞与下一步。
9. 结论：总体状态、可用性、是否进入下一阶段、人工复核要求；仅有实际统计时填写通过比例。

状态只使用 PASS（实际通过）、FAIL（实际失败）、BLOCKED（外部条件阻塞）、
NOT TESTED（未测试）、PARTIAL（部分通过）。不得编造数据、截图或测试结果，不得隐去重要失败。
日志与证据中禁止保存密钥、密码、PAT、JWT、真实个人隐私。

## 长期文档结构

统一采用以下结构；已有历史文档保留，通过索引链接，避免破坏既有引用：

```text
AGENTS.md
docs/
  DEVELOPMENT_LOG_POLICY.md
  development-log/
    README.md
    YYYY-MM-DD_HH-mm_任务名称_开发验收.md
  architecture/
    README.md
  product/
    README.md
  design/
    README.md
```

- architecture：架构、API 边界、技术选型与决策背景。
- product：版本范围、功能完成状态、验收项与已知限制。
- design：现有视觉 Token、组件复用原则、交互与响应式规范。
- development-log：每次实际开发的实现、修改明细、测试、证据、风险与结论。

任务引起跨模块决策或功能范围变化时，同步更新对应索引或文档。
禁止提前创建未来日期的“已验收”日志。示例日期与文件名仅作命名参考。
该制度对未来所有 Codex 开发任务持续生效。
